Magnetar

post-quantum RV64 zkVM from standard hashes hash-only transparent 120-bit provable Rust

Magnetar proves executions of general-purpose RV64I programs with every computational assumption rooted in standard hash functions — SHA-3 for Fiat–Shamir transcripts, BLAKE3 for the single Merkle commitment. This repository is the complete, tested implementation of the paper Magnetar: High-speed post-quantum RV64 zkVM from standard hashes (eprint 2026-2423): every component of the protocol runs, proves, verifies, and rejects tampering.

One commitment

MosaicPCS packs every committed polynomial — the direct witness segments and the memory arguments' one-hot components and increments — onto aligned subcubes of one cube, and commits once.

Hash-only security

No curves, no lattices, no trusted setup, no conjectured proximity gaps — the 120-bit bound uses only proven gaps inside the unique-decoding radius.

Sum-check native

The whole stack is multilinear sum-checks over binary fields: the prover's work is linear in the trace length and every argument is field-element sized.

Fully integrated

The seven-step Construction 3 runs end-to-end: Virtual Spartan, two BinaryTwists, two BinaryRouters, BinaryShout, and the final PCS evaluation argument.

The protocol, end to end

  1. Execute. The interpreter runs the microcode-expanded program and records the trace plus the memory-access log.
  2. Commit. The direct segments and the auxiliary polynomials form one MosaicPCS polynomial; the protocol's only commitment.
  3. Virtual Spartan. The two SIMD R1CS relations (F₂ bit constraints and F₂¹²⁸ packed products) reduce jointly to one claim per witness segment — the virtual claims are forwarded, the direct claims held.
  4. Reduce the virtual claims. BinaryTwist for registers and RAM (with the Ψ-sum-checks binding the address and index claims), BinaryRouter for shifts and sub-word stores (with the register-shift stage-select sum-check binding the conditional amount bits), BinaryShout for the bytecode.
  5. Prove the committed evaluations. MosaicPCS lifts each claim for free (aligned subcubes), batches them with one sum-check, and ring-switches to the packed polynomial for the single PCS evaluation argument — one argument for every segment in the claim-aggregated mode.

Quick start

git clone https://github.com/idrees2516/magnetar
cd magnetar
cargo test --workspace --release   # 69 tests: every argument + tamper classes
cargo run --release --bin magnetar -- fib 2

The last command executes a Fibonacci program, proves the execution, verifies the proof, and prints the measured cost model — the committed-bit inventory per component, the PCS geometry, and the byte breakdown of the proof (the PCS evaluation argument dominates, exactly as the paper's cost analysis predicts).

Horizon instruments

  • Claim aggregation. K segments of one program share ONE commitment and ONE evaluation argument; the byte-dominant part of the proof stays constant while the segment count grows (measured 3.46x at K=4 against the standalone counterfactual).
  • Dual-rate schedule. Chunk proofs commit at rate 1/2 for the fastest prover; the public artifact uses the conservative wrap profile — both measured by the instrumented CLI.
  • Register-shift stage-select. Register shifts prove end to end: the 6-stage trash-cell chain, the ROM-authenticated sel_stage one-hot, and the stage-selector sum-check composing the amount selector additively in characteristic two.
  • The measured cost model. The committed-bit inventory, the byte breakdown, the aggregation ledger, and the rate schedule — printed from the actual wire structure (cost-model.md).

The full engineering program — horizons, the recursion path, and the 150M-cycles/s GPU study — lives in the roadmap and the architecture deep-dives.

Security posture

  • Assumptions: SHA-3 (FIPS 202) and BLAKE3 only; transparent, no trusted setup.
  • Soundness accounting: sum-check round errors ≲ rounds·degree/|K|; the Δ*, Φ, Ψ, routing, ring-switch, and fold-chain identities each carry ≤ 2⁻¹²⁸ error at 120-bit target — the full accounting is in docs/security.md.
  • Implementation hygiene: constant-time field arithmetic, #![forbid(unsafe_code)] everywhere except the audited clmul module, zeroized secrets, domain-separated transcripts.
  • Testing: every transmitted claim and round-message family has a tamper test; honest proofs and adversarial proofs both run in CI.
